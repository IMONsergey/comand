- Административный SSH-доступ к выбранному Linux-серверу подтверждён.

- Bootstrap обслуживает только HTTP на порту 80: ACME challenge из `/var/www/comand-acme`; остальные запросы к этому имени возвращают `404`.
- `nginx -t` и перезагрузка Nginx завершились успешно.
- Локальный запрос с Host `comand.imon.world` к `/.well-known/acme-challenge/comand-preflight` вернул `comand acme ready`.

Последняя проверка подтверждает локальную маршрутизацию Nginx и чтение challenge-файла. Она **не подтверждает** существование DNS-записи, внешнюю доступность или выпуск TLS-сертификата.

На этом контрольном этапе A-запись `comand.imon.world` отсутствовала, сертификат ещё не выпущен, `publicUrl` hub ещё не переключён. ## Подготовленная конечная конфигурация

[deploy/comand.imon.world.conf](../deploy/comand.imon.world.conf) содержит целевой HTTP/HTTPS virtual host: HTTP challenge, перенаправление остальных HTTP-запросов на HTTPS и proxy к `127.0.0.1:4310`.

Это **подготовленный файл**, а не описание уже установленного bootstrap. Его HTTPS-блок ссылается на `/etc/letsencrypt/live/comand.imon.world/`; применять этот файл целиком до выпуска сертификата нельзя. Также перед применением нужно проверить наличие указанных общих файлов настроек TLS.

Прокси сохраняет публичный Host, передаёт HTTPS-схему, допускает тело 5 MiB и отключает buffering. `X-Forwarded-For` перезаписывается реальным `$remote_addr`. Приложение доверяет только непосредственному loopback-прокси; подробнее в [OPERATIONS.md](OPERATIONS.md#tls-and-networking).

## Оставшиеся шаги

### 1. DNS и сертификат

1. В DNS-зоне `imon.world` создать указанную A-запись `comand → 201.34.145.204` с TTL `300`.
2. Проверить ответ авторитетных DNS-серверов и разрешение имени извне. Не считать локальный Host-header запрос проверкой DNS.
3. Проверить внешний HTTP-доступ к challenge-файлу.
4. Выпустить сертификат через существующий Certbot и webroot `/var/www/comand-acme` для `comand.imon.world`.
5. Проверить файлы сертификата, установить подготовленный HTTPS virtual host, выполнить `nginx -t` и только после успешной проверки reload.
6. Проверить HTTPS с нормальной валидацией сертификата; обход проверки TLS не является успешной приёмкой.

### 2. Настройки существующего hub

Перед изменением сохранить папку состояния существующего Linux hub: остановить hub для согласованной копии SQLite и сохранить также `hub.json`, owner key и OAuth-файлы. Ключи и резервные копии не помещать в Git.

Следующие команды выполняются **от существующего пользователя ОС, которому принадлежит hub**, из его checkout:

```bash
cd "$HOME/Projects/comand"
node dist/cli.js init \
  --data-dir "$HOME/.comand/hub" \
  --host 127.0.0.1 \
  --port 4310 \
  --public-url https://comand.imon.world
node dist/cli.js service restart --kind hub --data-dir "$HOME/.comand/hub"
```

Для shell без user-bus environment использовать вариант из [OPERATIONS.md](OPERATIONS.md#linux-shells-without-a-user-bus-environment). Не создавать новый hub от root и не менять существующий owner key.

Существующий Linux agent может сохранить loopback URL: его bearer-запросы продолжают работать. Браузерный вход в этот hub после переключения выполняется через публичный HTTPS-origin. Вход с HTTP-loopback не соответствует ожидаемому Origin. Ключ публичной панели — ключ Linux hub, не отдельного локального Mac hub.

Проверить `/health`, вход в панель, обе OAuth metadata, корректный отказ неавторизованного `/mcp` и MCP-вызов с авторизацией. Metadata должны указывать на `https://comand.imon.world`, а не на loopback.

### 3. Подключение Mac к общему hub

Сначала проверить, что старые Mac-задачи завершены и нет неопределённого исхода. Старые `deviceId` и token принадлежат прежнему Mac hub: одной смены `hubUrl` недостаточно.

- Создать новый pairing в Linux hub и подключить Mac через HTTPS в отдельной папке состояния, например `~/.comand/agent-public`.
- Сохранить прежнюю `~/.comand/agent` и локальную историю Mac hub.
- До запуска нового агента остановить старую агентскую службу и убрать её из автозапуска. Два агента с разными папками состояния не координируют блокировки одних и тех же рабочих папок.
- Установить новую службу с её явным `--data-dir`; для браузерных задач сохранить `COMAND_BROWSER_CHANNEL=chrome`.
- Создать в общем hub проекты с новым Mac device ID и прежними разрешёнными canonical roots; перенести необходимые заметки. Автоматическое объединение старых историй задач не реализовано.
- Проверить реальные команды, журналы и чтение файла на обоих устройствах через общий hub.

### 4. OAuth и ChatGPT

При смене origin старые OAuth-подключения должны пройти авторизацию заново. Исправление проверки resource не допускает автоматический обмен старого refresh token на токен нового origin. Проверить существующие grants и отозвать прежние подключения, если они есть.

После успешной внешней проверки HTTPS зарегистрировать MCP URL `https://comand.imon.world/mcp` в целевом аккаунте ChatGPT, пройти OAuth и подтвердить настоящий вызов инструмента из этого аккаунта. Доступность функции в аккаунте и разрешения рабочего пространства проверяются отдельно; успешные тесты MCP SDK не заменяют эту проверку.

## Откат

- Для Linux восстановить сохранённый `hub.json` и конфигурацию нового virtual host, затем проверить Nginx и перезапустить службы. `init` без `--public-url` сохраняет уже заданный URL и не является командой его удаления.
- Для Mac остановить новую агентскую службу до возврата старой. Восстановить службу с прежним `data-dir` и выбранным Chrome; старые credentials не отзывать до успешного окончания переключения.
- Изменять или удалять только созданную для Comand DNS-запись и virtual host. Рабочие конфигурации других сервисов не участвуют в откате.
